# Rein — Phase 2 database implementation

Completed: October 21, 2026 (Asia/Manila).

Phase 2 establishes the first persistent data model for private tool libraries. The implementation lives in `backend/supabase/` and is designed for Clerk JWT subjects accepted through Supabase's native third-party authentication integration.

## Implemented schema

Migration `20261021070000_initial_library_schema.sql` creates `public.categories` and `public.tools`.

- UUID primary keys are generated by PostgreSQL.
- `user_id` stores the Clerk JWT `sub` as text and defaults from `auth.jwt()`.
- Category names are canonicalized by the application and enforced as trimmed, whitespace-collapsed values. A generated lowercase name supports per-owner uniqueness.
- Tools preserve the submitted URL and store an application-normalized URL plus lowercase hostname.
- Names, URLs, required descriptions, icon fields, statuses, timestamps, and positive versions have database checks.
- Duplicate normalized category names and tool URLs are rejected per owner.
- A composite foreign key from `(category_id, user_id)` to categories prevents cross-account category assignment.
- Populated categories cannot be deleted directly. Phase 4 will reassign their tools and delete the category in one transaction.
- Update triggers keep ids, owners, and creation timestamps immutable while incrementing `version` and refreshing `updated_at`.
- Owner/category and owner/creation indexes support the planned library reads.

## Authorization model

Row-level security is enabled on both tables. The `authenticated` role receives only SELECT, INSERT, UPDATE, and DELETE table privileges. Each operation has its own policy comparing `user_id` with the verified token subject from `auth.jwt() ->> 'sub'`; UPDATE checks both the existing and resulting row. The `anon` role has no table privileges.

Clerk remains the only identity store. There is no duplicate user table and no foreign key to `auth.users`. Native Clerk/Supabase provider configuration requires the project's Clerk domain and belongs to Phase 3. Local Phase 2 tests set the same JWT claim shape directly to verify policy behavior without credentials.

Account deletion cleanup is separate from ordinary category deletion. A later release gate must consume a verified Clerk user-deletion webhook and run idempotent privileged deletion of that subject's tools before categories. Until that handler exists, the product must not claim that deleting a Clerk account immediately erases library records.

## Seed and verification

`supabase/seed.sql` contains deterministic categories and tools for two mock Clerk subjects. It stores no passwords, tokens, or real user information.

The pgTAP suites cover schema shape, constraints, triggers, versioning, deletion restrictions, anonymous denial, two-user visibility, owner defaults, ownership transfer rejection, and cross-owner category references.

Verified commands:

```powershell
cd backend
npm run db:reset
npm run db:lint
npm run db:test
```

Results:

- Clean migration replay and seed: passed.
- Supabase database lint: no schema errors.
- Database tests: 3 files, 40 assertions, all passed.

## Phase 3 handoff

Phase 3 must configure Clerk and Supabase with the real Clerk domain, verify every protected Route Handler with Clerk's server API, and create user-scoped Supabase clients using the Clerk session token. It must also add request-origin protections, private response cache controls, and safe request logging. No secrets belong in migrations, seed data, tests, or documentation.
